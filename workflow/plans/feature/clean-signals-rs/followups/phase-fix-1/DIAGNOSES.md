## DIAGNOSIS
**Issue:** Confirmed. `FailureSink::emit` (controller.rs:136-141) takes `self.listeners.lock().unwrap()` and holds that `MutexGuard` for the entire duration of the listener-invocation loop, calling each `listener(failure)` while still holding the lock. `subscribe`'s removal closure (line 128) and `subscribe` itself (line 121) lock the very same `Arc<Mutex<Vec<(u64, Listener<F>)>>>` (shared via `Arc::clone`/`Arc::downgrade` in `Clone`/`subscribe`). This produces two real, distinct failure modes, both reachable with ordinary safe Rust (no `unsafe` needed):

1. **Permanent poisoning from a panicking listener.** If any user-supplied `listener(failure)` panics, the unwind drops the held `MutexGuard`, which marks the `Mutex` poisoned (std::sync::Mutex poisons on guard-drop-during-panic). Every subsequent `.lock().unwrap()` on that same Mutex — in `subscribe` (register), the `remove` closure (unsubscribe/`Drop for Subscription`), and any future `emit` — will itself panic on `PoisonError::unwrap()`. Since `FailureSink` is `Clone`-shared (same `Arc<Mutex<...>>>` across all controller/clone instances), one panicking listener permanently bricks failure delivery and, worse, breaks unrelated `Subscription::drop` calls for *other* listeners for the remaining life of the process/sink.
2. **Second panic → abort.** Because the poisoning happens as `emit`'s frame unwinds (inner frames unwind before outer ones), a `Subscription` for the *same* sink held live further up the call stack (e.g. `let _sub = sink.subscribe(...)` in the caller of `emit`, a very natural pattern such as a controller holding its own listener registration) will be dropped later in that same unwind, *after* the Mutex is already poisoned. Its `Drop` impl calls `remove()` → `.lock().unwrap()` → panics again while the thread is already unwinding from the first panic → Rust aborts the process (panic-while-panicking is not recoverable). This realizes the reviewer's "double-panic/abort" concern concretely.

Separately, the doc comment's stated re-entrancy caveat (module docs `controller.rs:93-99`: a listener must not `subscribe`/drop a `Subscription` of the *same* sink synchronously, or it deadlocks) is also verified accurate as currently written: because the lock is held across invocation, any such reentrant call self-deadlocks (non-poisoning, just a hang) on the non-reentrant `std::sync::Mutex`.

**Root cause:** crates/clean-signals/src/controller.rs:136-141 (`FailureSink::emit`). The `MutexGuard` returned by `self.listeners.lock().unwrap()` at line 137 is kept alive across the `for` loop at 138-140 that calls user-supplied `listener(failure)` (line 139). `Listener<F>` is `Box<dyn Fn(&F) + Send + Sync>` (line 56) stored in `Listeners<F> = Arc<Mutex<Vec<(u64, Listener<F>)>>>` (line 59), the same Arc/Mutex that `subscribe` (line 121) and its generated `remove` closure (line 128, via `Weak` upgrade of the same Arc) also lock. A panic inside any listener unwinds through `emit`, drops (poisons) that guard, and every later `.lock().unwrap()` call on the shared mutex (in `subscribe`, `remove`, or a later `emit`) panics on the resulting `PoisonError`. If a `Subscription` for the same sink is dropped later in the same unwind (outside `emit`'s frame, after the poison has been set), that second `.lock().unwrap()` panic occurs while the thread is already panicking, which Rust escalates to `abort()`.

**Fix approach:** Minimal, preserves subscription-order and actually eliminates the documented re-entrancy caveat rather than just working around it:
1. Change `Listener<F>` from `Box<dyn Fn(&F) + Send + Sync>` to `Arc<dyn Fn(&F) + Send + Sync>` (controller.rs:56) so entries are cheaply cloneable. Update `subscribe` (line 121) to push `Arc::new(f)` instead of `Box::new(f)`.
2. Rewrite `emit` to lock only long enough to clone the ids+Arcs into a local `Vec<(u64, Arc<dyn Fn(&F)+Send+Sync>)>` (or just `Vec<Arc<...>>>`, order preserved since the backing Vec is retain-order/subscription-order), drop the guard, then iterate the local Vec and invoke listeners with no lock held:
   ```rust
   pub fn emit(&self, failure: &F) {
       let snapshot: Vec<_> = self.listeners.lock().unwrap()
           .iter().map(|(_, l)| Arc::clone(l)).collect();
       for listener in snapshot.iter() {
           listener(failure);
       }
   }
   ```
   This preserves subscription-order emission (clone preserves Vec order) and means a panic in a listener no longer occurs while any MutexGuard from this sink is held, so the Mutex is never poisoned by a listener panic, and the abort chain described above cannot occur.
3. This change also *fixes* (not just documents) the re-entrancy caveat: since the lock isn't held during invocation, a listener may now safely call `subscribe` or drop a `Subscription` of the same sink synchronously without deadlocking (update the module doc at lines 93-99 to reflect this — note the one remaining subtlety: unsubscribing mid-emit won't retroactively stop that listener firing in the *current* emit pass since the snapshot was already taken, only future emits).
4. Lower-priority hardening (not required to fix the core bug, but worth doing since it's cheap and the reviewer flagged it): the other `.lock().unwrap()` sites in this file (`cleanups` at 388/430, `watches` at 371/422) are on separate, unrelated `Mutex` instances not touched by `emit`'s panic, so they are not affected by this specific bug and don't need to change for this fix; leave `unwrap()` there unless doing a broader poisoning-hardening pass.

**Files:** crates/clean-signals/src/controller.rs

**Regression risk:** Low. The change only touches `FailureSink` (type alias, `subscribe`'s push, and `emit`'s body); `Subscription`, `WatchHandle`, `ControllerCore` and its other mutexes are untouched. Behavior changes: (a) a listener panic no longer poisons the shared mutex — strictly safer, and existing tests (`failure_sink_fans_out_to_all_subscribers`, `failure_sink_dropped_subscription_stops_firing`, `failure_sink_forgotten_subscription_keeps_firing`) don't exercise panicking listeners so they're unaffected; (b) subscription-order is preserved because cloning a Vec preserves order; (c) a listener that unsubscribes another listener (or itself) mid-emit no longer sees that removal reflected in the current emit pass (it will still fire once for the in-flight emit, only future emits skip it) — this is a minor semantic shift from 'holds the lock, so retain() during remove and iteration would actually deadlock today anyway' to 'safe but slightly different (one-more-fire) semantics', which is arguably the same or better than current (current documented behavior is 'deadlock', so any change here is strictly an improvement, not a regression against real usage). **Issue:** Confirmed: `ControllerCore::watch()` (crates/clean-signals/src/controller.rs:339-375) and `ControllerCore::dispose()` (crates/clean-signals/src/controller.rs:416-437) are two independent critical sections over the same `watches: Mutex<Vec<AbortHandle>>` field, with no coordination between `watch()`'s registration and `dispose()`'s idempotent drain. `ControllerCore<F>` is unconditionally `Send + Sync` and is documented (task 06 completion notes, `docs/ARCHITECTURE.md`) as deliberately so for `leptos::StoredValue`/`provide_controller` (Arc-based, app-scoped) usage, so cross-thread concurrent calls are a real, sanctioned scenario, not a theoretical one.

Race sequence that reproduces the leak:
1. Thread A calls `watch()`: builds the stream, spawns the driver task via `Executor::spawn_local` (line 367-369) — the task starts running immediately/concurrently.
2. Before A reaches line 371 (`self.watches.lock().unwrap().push(abort_handle.clone())`), Thread B calls `dispose()`: `disposed.swap(true, ...)` succeeds (line 417), it locks `watches` and drains/aborts everything currently registered (line 422-424, A's handle isn't there yet), runs cleanups, returns.
3. A then pushes its `abort_handle` into `watches`. Because `dispose()`'s first line makes it idempotent (`if self.disposed.swap(true,...) { return; }`, line 417-419), no future call to `dispose()` will ever drain/abort this handle again — it is permanently orphaned.
4. A's driver task is not aborted. Its only remaining defense is the per-item `disposed.load(Ordering::SeqCst)` check at line 357, which only runs *after* `stream.next().await` resolves. If the stream is long-lived/low-frequency (or simply blocked waiting on the next item), the task keeps polling (i.e., stays alive/scheduled, holding the stream's resources) for an unbounded time after `dispose()` — it is not aborted immediately the way every other correctly-registered watch is. `on_data` itself still won't fire once an item does arrive (the flag check runs before the match), but the "aborted immediately by dispose, no lingering driver" contract stated in the doc comment at controller.rs:334-335 is violated for this specific watch.

This exact finding (with matching line numbers and mechanism) is already recorded as F5 in this repo's own prior review artifacts (`workflow/reviews/clean-signals-rs/findings-confirmed.md` lines 41-47, `workflow/reviews/clean-signals-rs/REVIEW.md` line 17), independently corroborating the trace above. It is a distinct issue from the related, also-confirmed F3 ("watches Vec grows unbounded" / registry never pruned) even though both touch the same `self.watches: Mutex<Vec<AbortHandle>>` field and the same `watch()`/`dispose()` code.

**Root cause:** crates/clean-signals/src/controller.rs:339-375 (`watch`) and :416-437 (`dispose`). `watch()` spawns the driver task (line 367-369) and only afterward takes `self.watches.lock()` to push the `AbortHandle` (line 371) — it never checks `self.is_disposed()` at all. `dispose()` (line 417) does an unsynchronized `AtomicBool::swap` to become idempotent, then separately locks `self.watches` to drain+abort (line 422-424). Because the "am I disposed" flag flip and the "drain watches" step in `dispose()`, and the "spawn + register" step in `watch()`, are not performed as one atomic operation under a shared lock, a `watch()` call whose push (line 371) lands after a concurrent `dispose()`'s drain (line 422-424) has already run leaves its `AbortHandle` permanently unregistered (dispose is a no-op on subsequent calls, line 417-419) and its driver task never explicitly aborted. The per-item `disposed.load()` guard at line 357 is a secondary, best-effort check that only fires after the next stream item is polled, so it does not stop the task from continuing to poll (i.e., run) indefinitely in the meantime — it only prevents that lingering task's `on_data`/failure-emit side effects, not its continued existence/resource use.

**Fix approach:** Make the flag-flip/drain in `dispose()` and the check/register in `watch()` share one lock so they can't interleave, rather than documenting a single-threaded-only contract (the type's Send+Sync is already load-bearing for `provide_controller`'s Arc-based, potentially cross-thread app-scoped use — narrowing to single-threaded-only would contradict already-shipped API surface).

Concretely:
1. In `dispose()`: acquire `self.watches.lock()` FIRST, then do the idempotency check/flag-flip (`self.disposed.swap(true, Ordering::SeqCst)`) while still holding that lock, then drain+abort, then drop the lock before running cleanups/owner.cleanup() (those don't need to be inside the critical section and may themselves call back into the controller, e.g. via `on_dispose`).
2. In `watch()`: acquire the SAME `self.watches` lock as the very first step, then check `is_disposed()` while holding it. If disposed, return a dead `WatchHandle` (an already-aborted `AbortHandle`, or a `WatchHandle` whose `cancel()` is a no-op) WITHOUT calling `uc.execute(params)` or spawning anything. If not disposed, proceed to build the stream/driver, spawn it, and push the `AbortHandle` into the vec, all still under the same lock (spawning under a lock is fine here since `Executor::spawn_local` just hands the future to the executor and returns; it doesn't itself try to re-lock `watches`).
3. This makes the two operations strictly ordered: either `watch()`'s check-then-register happens entirely before `dispose()`'s flip-then-drain (so dispose sees and aborts the new handle), or entirely after (so `watch()` sees `disposed == true` and never spawns). No interleaving is possible, eliminating the TOCTOU without needing a second/ordered lock — there is only the one `watches` Mutex in play, so no new lock-ordering rules are introduced.
4. Coordinate with the F3 fix (making `watches` a prunable, id-keyed registry instead of an append-only `Vec<AbortHandle>`): since both fixes touch the same field/critical sections, do them together — the redesigned registration path (insert-with-id) should be the same code path that gets the `is_disposed()` check added, avoiding two separate lock-shape changes to the same code.

**Regression risk:** Low-to-moderate.
